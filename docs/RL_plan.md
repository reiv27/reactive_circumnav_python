# План: постановка задачи RL для компенсации задержек

Сопроводительный документ к анализу `delay_oscillations_research.tex`. Там RL
отнесён к методам низкого приоритета для этой системы («модель Дубинса проста
и хорошо известна, отказ от model-based predictor в пользу RL трудно
оправдать»), но ниже — корректная постановка задачи, если/когда до неё дойдёт
очередь (после этапов predictor feedback / HOSM / HOCBF, см. README и
`AGENTS.md`).

**Статус (2026-10-13): постановка + первый учебный набросок.** Код в
`src/circumnav/rl/` (`CircumnavEnv`, `circumnav-rl-train`) реализует
постановку (a) из раздела 1 без задержек — как упражнение для освоения RL на
этой задаче, а не как претензию обогнать `PredictorController` (раздел 5 всё
ещё в силе: в номинальном случае он по построению не может быть хуже). См.
примечание в конце документа.

## 1. Зачем это может быть нужно

Не как замена точному predictor'у (этап 1 плана), а как инструмент для
режима, где кинематическая модель или величина задержки **неизвестны или
нестационарны** — там, где model-based реконструкция (точная, но требует
знания `τ` и модели объекта) менее устойчива. Это соответствует «Этапу 5»
общего плана (робастность: шум, рассогласование модели, джиттер).

Два варианта постановки, от простого к осмысленному:

- **(a) RL заменяет реле целиком** — учится управлению `ω(t)` напрямую по
  истории наблюдений. Простая baseline-постановка, полезна как референс, но
  вряд ли обгонит точный predictor в номинальном случае (известная модель,
  известная задержка).
- **(b) RL учит остаточную поправку (residual) над predictor+relay** —
  архитектура из отчёта: «model-based predictor + CBF safety shield, learning
  только для residual dynamics или оценки неизвестного τ/model mismatch».
  Более защитимая постановка: сеть компенсирует то, что модель
  **не** знает (ошибка модели привода, непредсказанный `τ`, шум), а не
  переизобретает то, что уже решено точно.

## 2. Среда: чего не хватает в текущем коде

`Controller.compute(time, state) -> DubinsCommand` — уже шаговый интерфейс, но
`Simulator.run()` ([simulation/engine.py](../src/circumnav/simulation/engine.py))
исполняет весь эпизод синхронно за один вызов с готовым объектом-контроллером.
**Предварительный шаг, без которого обучение не начать**: степабельная
обёртка в духе Gym/`gymnasium.Env` (`reset() -> observation`,
`step(action) -> (observation, reward, terminated, truncated, info)`), которая
продвигает симуляцию ровно на один `control_period` за вызов, используя те же
`DubinsModel`, `Actuator`, `Sensor`, `Obstacle`, что и сейчас — без изменения
их самих. Это отдельная, явно выделяемая подзадача (новый модуль, например
`circumnav/rl/env.py`), не связанная с `Simulator`/`Scenario` изменениями.

## 3. MDP-постановка

### Наблюдение

Нельзя отдавать агенту голую мгновенную позу под задержкой — это нарушает
марковость. Стандартное решение (на него же ссылается и сам отчёт: «RL может
работать с delay через history-augmented state») — расширить наблюдение
историей собственных последних действий длиной `⌈τ_max/T⌉`, где `τ_max` —
верхняя граница задержки в текущем домене рандомизации. Состав вектора
наблюдения на шаге `t`:

- сырые измерения сенсора: `P1` (dist, bearing), `P2` (dist, bearing) или
  флаг «не видно» — то, что реально доступно контроллеру сейчас
  (`sensors/circular.py`), не истинная геометрия препятствий;
- собственная история из последних `k` выданных команд `(speed, yaw_rate)`
  — тот же трюк, что у model-based предиктора (там это точная кинематика,
  здесь сеть должна **выучить** эквивалент `propagate`);
- опционально: текущий режим `C/G`, если задача ставится как «residual» над
  существующим реле (тогда режим уже известен из `inner.log`).

### Действие

`speed` фиксирован (`forward_speed`), свобода — только в `yaw_rate`. Два
варианта:

- continuous `ω ∈ [-ω_max, ω_max]` — PPO/SAC, естественно для постановки (a);
- дискретное бинарное `{-ω_max, +ω_max}` — сохраняет бэнг-бэнг структуру
  существующего закона, задача становится «когда переключать знак», более
  прямое сравнение с релейным законом и лучше подходит для постановки (b)
  (residual как редкие коррекции момента переключения).

### Награда

Переиспользовать существующие метрики буквально, не изобретать новые:

```
r_t = -|d_R(t)| - λ_u * |u_t - u_{t-1}|
```

плюс большой терминальный штраф при `clearance < collision_distance` —
то же условие, что уже считает
[`obstacle_clearance_metrics`](../src/circumnav/analysis/metrics.py).
`d_R`, режим и `u_t` уже лежат в `controller.log`
(`ReactiveLogEntry.equidistant_deviation`, `.range_rate`), их не нужно
пересчитывать отдельно.

### Эпизод

Один эпизод = один прогон сценария (`ReactiveCircumnavScenario`-эквивалент):
фиксированная или рандомизированная сцена препятствий, случайные начальные
`(x0, y0, heading0)` в окрестности существующих значений по умолчанию,
ограничение по времени `duration`.

## 4. Доменная рандомизация делает задачу честной

Обучать на **распределении** задержек `(τ_s, τ_a, τ_ℓ)` за эпизод, не на
одном фиксированном значении — соответствует «Этапу 2/4» общего протокола
(delay-mismatch, jitter из `delay_oscillations_research.tex`). Иначе политика
просто переобучится на один конкретный `τ`, и сравнение с predictor'ом
(который честно получает точное `τ`) будет нечестным в его пользу или в
пользу RL в зависимости от того, какое `τ` зашито в обучение.

Параметры рандомизации по эпизоду:

- `τ_s, τ_a, τ_ℓ ~ U(0, τ_max)` каждый независимо (иногда 0, иногда
  совместно несколько ненулевых — joint delays);
- опционально джиттер `τ(t) = τ̄ + η(t)`, `|η(t)| ≤ J` — нестационарная
  задержка внутри одного эпизода;
- опционально шум измерения `P1`/`P2`, ошибка модели (`v`, `ω_max`), чтобы
  тестировать именно то, где RL может выиграть у model-based подхода.

## 5. Как сравнивать с этапом 1 (predictor feedback)

Контрольный эксперимент — не «RL vs ничего», а **RL vs точный predictor** на
одних и тех же сценах и метриках:

- те же метрики, что в `delay_sweep.py` / `delay_compare.py`: `max|d_R|`,
  частота переключений реле, `minimum_clearance`, `collided`;
- одинаковые сетки `τ` (как в «Этапе 1» и «Этапе 2» общего протокола);
- ожидаемый (проверяемый) результат по гипотезе отчёта: в номинальном случае
  (известная модель, известная задержка) RL **не превосходит** точный
  predictor; RL интереснее там, где модель или `τ` неизвестны/шумны —
  то есть как инструмент этапа робастности, а не как замена этапа 1.

Если гипотеза не подтвердится (RL выигрывает даже в номинальном случае) —
это сигнал, что реализация model-based предиктора (этап 1) содержит ошибку,
а не что RL действительно лучше: кинематика здесь точно известна, и
model-based подход по построению не может быть хуже в этом случае.

## 6. Возможный стек для реализации (на будущее, не сейчас)

`gymnasium.Env` для среды, `stable-baselines3` (PPO для continuous,
DQN/ambient для discrete) как референсные алгоритмы — без собственной
реализации RL-алгоритма, чтобы не плодить лишний код в проекте, у которого
единственная runtime-зависимость — `numpy`. Это новая опциональная
зависимость (`rl` extra в `pyproject.toml`), по аналогии с существующим
`viz` extra для matplotlib.

## 7. Открытые вопросы перед реализацией

1. Нужна ли степабельная обёртка как переиспользуемая инфраструктура, или
   достаточно одноразового скрипта под конкретный эксперимент?
2. Постановка (a) или (b) — полная замена реле или residual-поправка?
   Решает это, какие тесты/baseline нужны и насколько инвазивно устройство
   среды относительно существующего `ReactiveCircumnavController`.
3. Дискретное или continuous действие — зависит от (2).
4. Нужен ли отдельный safety-shield (HOCBF, этап 3) поверх RL-политики на
   этапе обучения (чтобы не терять эпизоды на коллизиях) или только на
   этапе оценки?

Эти вопросы стоит закрыть явно с пользователем перед тем, как заводить
`rl`-зависимость и новый модуль, а не решать их implicit в процессе
реализации.

## 8. Статус: что уже сделано (ветка `rl/ppo-ellipse-sketch`)

Пользователь решил разобраться в RL на практике, не дожидаясь очереди по
приоритету из раздела 0 — поэтому ниже первый набросок, а не финальный
дизайн; вопросы из раздела 7 закрыты в пользу самого простого рабочего
варианта, не самого защитимого:

1. **Степабельная обёртка — переиспользуемый модуль**: `circumnav/rl/env.py`,
   `CircumnavEnv(gymnasium.Env)` + `CircumnavEnvConfig`. Повторяет
   ZOH-структуру `Simulator.run`, использует те же `DubinsModel`, `Actuator`,
   `CircularVisibilitySensor` без изменений.
2. **Постановка (a)**: полная замена реле. `P2` берётся той же геометрией
   диска, что и в `ReactiveCircumnavController` (не часть замороженного
   закона, просто способ предъявить сенсор), поэтому у агента то же
   наблюдение, что было бы у реле.
3. **Действие — continuous** `ω ∈ [-ω_max, ω_max]`, алгоритм — PPO
   (`stable-baselines3`), как и предполагал раздел 3 для постановки (a).
4. **Safety shield — не реализован.** HOCBF (этап 3 общего плана) ещё нет;
   коллизия просто обрывает эпизод терминальным штрафом (`collision_penalty`).
   Это самый дешёвый вариант из раздела 7, не самый бережный к сэмплам.

Без задержек (`sensing_delay=0`): цель первого прогона — проверить, что
среда и PPO-baseline работают end-to-end на одном эллипсе, не инструмент
робастности из раздела 1 — тот эксперимент (доменная рандомизация по `τ`,
раздел 4) ещё впереди, если пользователь захочет продолжить.

`circumnav-rl-train --shape ellipse` обучает и сохраняет сравнение с
baseline-реле на том же сценарии (`simulation_output/<shape>_rl_compare.png`).
Тесты: `tests/test_rl_env.py` (контракт среды, не качество политики).
